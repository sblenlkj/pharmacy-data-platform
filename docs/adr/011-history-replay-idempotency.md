# ADR 011: история версий и идемпотентный повтор порции по batch_id

**Статус:** принято (механика merge-replay по естественным ключам подтверждена
spike 1, 2026-11-15/16; журналами трёх прогонов и обслуживанием Iceberg —
2026-11-17, см. «Обслуживание таблиц Iceberg» и [журнал
загрузок](../load_journal.md)).

## Контекст

Чекер ДЗ-2 требует:

1. предыдущие версии товара и цены сохраняются: смена названия SKU и цены
   закрывает открытую версию и открывает новую, старые строки чеков
   сохраняют исходный снимок;
2. `./scripts/load_dds --batch-id ID --replay` повторно применяет сохранённый
   диапазон той же порции без дублей строк и без лишних версий истории;
3. интервалы `[valid_from, valid_to)` без пересечений, открытая версия —
   `valid_to IS NULL`;
4. в `v_load_batches` — ровно одна строка на `batch_id` со статусом и
   диапазонами offsets, границы при повторе не меняются.

## Решение

### История из событий, а не из состояния

Источник уже версионирует атрибуты (`sku_version`, `price_version` —
см. [ADR 001](001-history-strategy.md)). Загрузчик не вычисляет версии, а
проецирует события CDC:

- `dim_sku_version` — одна строка на `(sku, valid_from)` из событий
  `catalog.sku_version`; `valid_to` источником не хранится и выводится
  как `valid_from` следующей версии (открытая — `NULL`);
- `dim_price` — одна строка на `(sku, price_scope, scope_bk, valid_from)`
  из событий `catalog.price_version`; `valid_to` приходит событием
  закрытия (UPDATE), применяется только если `valid_to IS NULL`
  (guarded update);
- атрибуты, у которых в источнике был только текущий срез, начинают
  историю с первого снимка (`op='r'`): дата снимка → `valid_from`
  открытой версии.

### Идемпотентность по естественным ключам

Каждая строка DDS merge-ится по естественному ключу:

| Таблица | Ключ merge |
|---|---|
| `fact_sale_line` | `(receipt_bk, line_no)` |
| `fact_purchase_line` | `(purchase_bk, line_no)` |
| `fact_movement` | `movement_bk` |
| `dim_sku`, `dim_customer`, `dim_pharmacy`, `dim_batch`, `dim_supplier`, `dim_distribution_center` | бизнес-ключ |
| `dim_sku_version` | `(sku, valid_from)` |
| `dim_price` | `(sku, price_scope, scope_bk, valid_from)` |

Повторное применение тех же событий (те же offsets) даёт те же значения
тех же ключей → merge завершается без изменений. Единственная
нетривиальная операция — закрытие `valid_to`: guard «обновлять только
NULL» гарантирует, что повтор не сдвинет границу и не создаст версию.

Все значения строк DDS вычисляются только из payload событий: в моделях
запрещены `now()`, `current_timestamp` и прочие недетерминированные
функции — иначе повтор порции не воспроизводил бы значения байт-в-байт.

Детерминизм SCD1-справочников (`dim_customer`, `dim_sku`, `dim_pharmacy` …)
при повторе порции: «последний выигрывает» упорядочиванием по координатам
Kafka `(topic, partition_id, kafka_offset)`, а не по времени загрузки —
иначе повтор порции менял бы текущий срез на более старое значение.

### No-op MERGE всё равно создаёт снапшот Iceberg

Наблюдение spike 1 (HMS-каталог): INSERT + MERGE + повторный MERGE тех же
строк → в таблице 3 снапшота Iceberg, хотя второй MERGE не изменил ни одной
строки (счётчик 0 rows). Следствия:

- признак no-op при повторе порции — счётчик вставок/обновлений MERGE
  (0 rows), а не «снапшотов не прибавилось»: replay-логика и журнал
  прогона не опираются на число снапшотов;
- каждый повтор порции добавляет снапшоты и метаданные Iceberg — при
  штатных повторах (replay чекера) и доначлениях накопление ограничено,
  но бесконтрольным его оставлять нельзя.

### Обслуживание таблиц Iceberg

Единая точка обслуживания — `scripts/hw2/maintain_iceberg.py` (Trino 484:
`ALTER TABLE … EXECUTE expire_snapshots / optimize / remove_orphan_files`,
метрики — таблицы `«имя$snapshots»`/`«имя$files»`). По каждой физической
таблице `dwh_detailed` (автообнаружение через information_schema) и
`raw.cdc_events`: метрики до → expire_snapshots → optimize →
remove_orphan_files → метрики после, с таймингом каждой операции.

**Когда.** Один раз на старте стенда: dwh-init после успешной начальной
загрузки — маркер `INITIAL DDS LOAD DONE` → обслуживание → финальный
маркер `ICEBERG MAINTENANCE DONE` (чекер запускать после него). Плюс
ручной запуск той же командой. В `scripts/load_dds` обслуживание **не
входит**: чекер меряет команды load по таймауту 90 с (дельта 45 с, replay
32–41 с), обслуживание — отдельный шаг вне тайм-пути; на повторном
up/dwh-init сворачивается в no-op.

**Retention.** По умолчанию `7d` — консервативный производственный порог
(time-travel на неделю) и одновременно системный минимум Trino
(`iceberg.expire-snapshots.min-retention`, ниже — только session-свойством
на своём подключении). `remove_orphan_files` с порогом 7d удаляет только
файлы старше недели — файлы in-flight записи (cdc-ingest) моложе порога и
не затрагиваются, гонка с пишущим сервисом исключена по построению.
Агрессивный порог (`--retention 0d`) — осознанный режим учебного стенда:
один процесс-писатель, конкурентных читателей и time-travel нет.

**optimize идемпотентен по построению Trino:** переписываются только файлы
<100 МБ при >1 файле в партиции или наличии delete-файлов; нечего
переписывать → 0 файлов и **новый снапшот не создаётся** (повторный запуск
— 12→12 снапшотов, 4.8 с на 12 таблиц).

**Факты замеров** (2026-11-17, стенд после приёмочного прогона):

| Прогон | Снапшоты | Файлы (данные+delete) | Размер | Время |
|---|---|---|---|---:|
| 1: штатный `--retention 7d` | 358 → 370 | 427+57 → 49+0 | 13.0 → 8.8 МБ | 12.0 с |
| 2: `--retention 0d` (демо) | 370 → 12 | — | — | 8.4 с |
| 2b: то же + orphan-порог 0d | 12 → 12 | — | −68.4 МБ в S3 (534 файла raw) | 5.6 с |
| 3: повтор штатного | 12 → 12 (no-op) | 49 → 49 | 8.8 МБ | 4.8 с |

Эффекты: expire с 7d на свежем стенде снимает 0 (снапшоты моложе порога —
накопление ограничено временем жизни стенда, при длинной жизни срабатывает
тот же запуск); optimize устранил все delete-файлы MERGE-загрузок и сжал
raw с 316 файлов до 1 (в файлах фактов — половина строк была «мёртвыми»
под delete-масками: fact_movement 184 290 → 92 144 записей); orphan-скан с
коротким порогом высвободил 68.4 МБ потерянных файлов raw (317 снапшотов
ingest-батчей + хвосты рестартов). Контрольные суммы 11 представлений данных
контракта до/после каждого прогона идентичны байт-в-байт. Полное чтение
тяжёлых представлений не замедлилось (v_sale_line ≈2.2 с, v_movement
≈2.2 с до и после), replay начальной порции на том же стенде — 59.5 с до
→ 41.5 с после (меньше файлов raw и отсутствие delete-файлов).

### Порция и её границы

- обычный запуск: загрузчик сам создаёт `batch_id` (UUID) и берёт
  диапазон `[saved_position, current_max_offset)` по каждому
  topic/partition из `raw.cdc_events`;
- `--batch-id ID`: тот же механизм, но переданный идентификатор
  сохраняется вместе с диапазонами в `ctl.load_batches`;
- `--replay`: диапазоны читаются из `ctl.load_batches` по `batch_id` и
  применяются той же merge-логикой; позиция обработки не двигается,
  строка порции не перезаписывается (статус остаётся `success`);
- позиция `ctl.kafka_positions` продвигается только после успешного
  завершения загрузки порции;
- `_load_batch_id` строки фиксирует порцию, впервые её записавшую; при
  повторе значение не меняется (merge по ключу), что и предъявляется
  в журнале прогона.

### Снимок продажи

`fact_sale_line` хранит snapshot-атрибуты позиции (`sku_name_snapshot`,
`is_rx_snapshot`) как физические колонки из события `pos.receipt_line`;
смена названия SKU в каталоге не затрагивает факт (проверка чекера
«снимок продажи прежний» выполняется автоматически).

## Рассмотренные альтернативы

1. **Хранить текущее состояние + вычислять историю при чтении.** Отвергнуто:
   представления контракта должны возвращать версии, а не выводить их
   на лету; риски расхождений при строгой сверке.
2. **Событийные сателлиты (Data Vault) как носитель истории.** Отвергнуто
   вместе с DV в [ADR 009](009-dds-model.md); механизм версий по
   `(ключ, valid_from)` даёт тот же эффект без лишнего слоя.

## Цена выбора

- no-op MERGE создаёт новый снапшот Iceberg (spike 1) — повторы порций
  накапливают метаданные; лечится обслуживанием при старте стенда и
  по необходимости вручную (см. «Обслуживание таблиц Iceberg»);
- сборные справочники (`dim_customer`, `dim_sku`): merge перезапускается
  событием главного маршрута (customer, sku); изменение ТОЛЬКО сателлита
  (профиль/согласия, состав ингредиентов) подхватится при следующем
  событии родителя — протокол чекера таких изолированных изменений не
  порождает, ручные правки сателлитов требуют догрузки родителя;
- эвристика готовности снапшота CDC («стабильные end-offsets 15 с» без
  прямого сигнала завершения от Debezium) при паузе снапшота длиннее
  окна может дать ранний маркер — остаток подберёт следующая порция;
- вывод `valid_to` для `dim_sku_version` требует перекрывающего окна по
  версиям SKU в staging-модели dbt;
- `--replay` не защищает от гонки с параллельным обычным запуском —
  загрузчик запускается одним процессом (блокировка через таблицу
  `ctl.load_batches`);
- **поздний replay старой порции** перезаписывает более позднее состояние
  (last-write-wins по payload): replay окна порции снова применяет её
  значения, и если позже другой порцией были изменены те же ключи
  (например, soft delete клиента фазой privacy), replay вернёт атрибуты
  на момент порции. Требуемая протоколом чекера семантика — повтор той же
  порции сразу после загрузки — выполняется (проверено сценарно); поздние
  replay нужно применять в хронологическом порядке порций (это же —
  способ восстановления состояния). Защита «не перезаписывать строку,
  если её координаты источника новее», возможна через сравнение
  `_src_*`-колонок при merge — осознанно отложена;
- журналы трёх прогонов (начальная, дельта, повтор — [журнал
  загрузок](../load_journal.md)): вставок/обновлений при повторе 0,
  контрольные суммы 11 представлений данных идентичны до/после — «подтвердить
  журналами» закрыто журналом загрузок и контрольными суммами в нём.
