# ADR 009: модель детального слоя DDS

**Статус:** принято (по результатам сравнения dimensional / Data Vault / Anchor Modeling).

## Контекст

ДЗ-2 требует собрать DDS для продаж, закупок и движений партий из четырёх
независимых источников (CRM, каталог, POS, WMS) с требованиями:

- контрактные представления `contract_dwh` с точным совпадением значений
  (~130 тыс. строк сверяются чекером ключ-в-ключ, любое расхождение — fail);
- история SKU и цен полуоткрытыми интервалами `[valid_from, valid_to)`
  без пересечений, `NULL` в `valid_to` — открытая версия;
- идемпотентный повтор той же порции по `batch_id` без дублей и лишних версий;
- связь каждой строки/версии с источником (topic/offset) и `batch_id`;
- soft delete клиента скрывает его из `v_customer`, но сохраняет чеки и суммы;
- инкрементальная загрузка поверх стека Trino + Iceberg + MinIO, наполняется dbt.

Бизнес-ключи уже гармонизированы в ДЗ-1 (`customer_bk`, `sku`, `batch_bk` …
используют одинаковый текстовый формат во всех четырёх системах,
[ADR 008](008-business-key-format.md)): задачи склейки конфликтуующих
ключей и master data management нет.

## Сравнение

| Критерий | Dimensional (Kimball) | Data Vault | Anchor Modeling |
|---|---|---|---|
| Маппинг на контракт `v_*` | 1:1 — представления суть звезда: `v_sku`/`v_customer`… = текущие срезы dim, `v_sku_history`/`v_price_history` = SCD2-слои, `v_sale_line`/`v_purchase_line`/`v_movement` = транзакционные факты | Складывается через fold-view из hub+sat+link (3–5 JOIN на представление) | Ещё больше JOIN: tie + anchor + attribute |
| История SKU/цен | Источники уже версионируются (`sku_version`, `price_version` с `valid_from/valid_to`); SCD2 — почти прямая проекция событий | Сателлиты по событию CDC дают историю «по построению» | То же, но с нормализацией атрибутов |
| Идемпотентный replay | Естественные ключи строки (`receipt_bk,line_no`; `sku,valid_from`; `sku,scope,scope_bk,valid_from`) + merge с проверкой позиции события — повтор тот же → no-op | Sat-строка с ключом по событию CDC — no-op по построению | Аналогично DV |
| Lineage (`batch_id`, источник) | Технические колонки `_load_batch_id`, `_src_topic/_src_partition/_src_offset` на строке | `load_batch_id` в сателлитах — идиоматично | Аналогично DV |
| Интеграция 4 источников | BK уже согласованы в ДЗ-1, склейка на staging-моделях dbt | Главный аргумент DV — разрешение конфликтных ключей из разных систем — здесь не нужен | То же |
| Объём таблиц/моделей dbt | ~8 dim + 3 fact + 3 технических | ~7 hub + ~12 sat + ~6 link + представления — в ~2,5 раза больше моделей | Больше DV |
| Риск расхождения при строгой сверке | Минимальный: представления — простые SELECT над dim/fact | Выше: каждое fold-view — точка ошибки на сотнях тысяч строк | Максимальный |
| Готовность к ДЗ-3 (витрины закупок и логистики) | Витрины строятся со звезды напрямую | Через PIT/focus-view — дополнительный слой | То же |
| Трудозатраты при дедлайне 01.12 | Базовые | Высокие | Максимальные |

## Рассмотренные альтернативы

1. **Data Vault.** Сильные стороны — аудируемость (сателлит на событие),
   устойчивость к изменению источников, идиоматичный lineage. Отвергнут:
   ключевая предпосылка DV — консолидация рассогласованных ключей и
   позднее связывание — отсутствует, ключи уже стандартизированы в ДЗ-1;
   ~2,5× числа таблиц и сложные fold-view увеличивают риск несовпадения
   значений в строгой сверке чекера без начисляемых за это баллов.
2. **Anchor Modeling.** Отвергнут: те же недостатки, что у DV, плюс ещё
   большая фрагментация; выигрыш только при массово эволюционирующей схеме,
   чего в учебном проекте нет.
3. **Dimensional modeling.** Выбрано.

## Решение

Звезда (Kimball) с SCD2-версиями и техническими колонками lineage:

- транзакционные факты `fact_sale_line`, `fact_purchase_line`,
  `fact_movement` — append/merge по естественному ключу, degenerate BK,
  snapshot-атрибуты позиции (`sku_name_snapshot`, `is_rx_snapshot`) как
  в источнике;
- справочники: `dim_sku` — только SCD1-атрибуты (`inn_name`,
  `manufacturer_name`, `drug_form`, `is_vital`, `pack_qty`, `is_active`);
  `dim_sku_version` (SCD2: имя, категория, признак Rx) — единственный
  носитель историзируемых атрибутов SKU: `v_sku` берёт текущие
  имя/категорию/Rx из открытой версии, что исключает рассинхрон с
  `v_sku_history` (чекер кросс-проверяет открытую версию против текущего
  состояния `v_sku`); `dim_price` (SCD2 по области действия),
  `dim_customer`, `dim_pharmacy`, `dim_batch`, `dim_supplier`,
  `dim_distribution_center`;
- производные значения (`line_amount`, `line_cost`, `is_current`)
  вычисляются в представлениях по формулам источника
  ([ADR 006](006-derived-fields.md)), а не хранятся в фактах;
- суррогатные ключи не вводим: BK ДЗ-1 стабильны и уникальны
  (обоснование — [ADR 008](008-business-key-format.md)), естественные
  ключи упрощают dbt-merge и представления;
- на каждой строке dim/fact — `_load_batch_id` и координаты события
  источника `_src_topic`, `_src_partition`, `_src_offset`;
- soft delete клиента разрешается на уровне представлений: `v_customer`
  фильтрует удалённых, `v_sale_line.customer_bk` и `v_movement.dst_bk`
  зануляются LEFT JOIN к видимым клиентам — семантика повторяет ADR 007.

## Цена выбора

- Перед DDS поддерживается текущее обработанное состояние физических
  источников `dwh_staging.stg_source_state`. Guard по offset применяется
  там: старый replay не отменяет уже полученное закрытие версии цены;
- lineage живёт колонками, а не отдельными сателлитами: смена источника
  поля требует миграции колонок;
- полиморфные endpoints движения (`src_type`/`src_bk`/`dst_type`/`dst_bk`)
  остаются denormalized атрибутами факта, ссылочная целостность по типу
  проверяется представлением (как в ADR 005).
