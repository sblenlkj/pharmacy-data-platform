# Interesting Facts — HW1

Небольшие наблюдения по заданию, которые легко пропустить при проектировании.  
Сюда записываем не общий план, а именно такие детали, которые нашли при чтении README, контракта, инвариантов и чекера и не хотим забыть.

## 1. Snapshot требуется не для всех справочных данных

В задании явно требуются snapshot-поля именно для:

- цены на момент продажи;
- названия SKU на момент продажи;
- признака рецептурности на момент продажи.

То есть в POS строка чека должна хранить собственные:

- `unit_price`;
- `sku_name_snapshot`;
- `is_rx_snapshot`.

Не нужно автоматически копировать в чек вообще все данные из Catalog.  
Если для какого-то другого атрибута snapshot понадобится, это должно быть отдельным осознанным решением, а не следствием общего требования.

## 2. Soft delete требуется прежде всего для справочников

Формулировка задания: **soft delete вместо физического DELETE в справочниках**.

Это не означает, что каждая таблица должна обязательно иметь `is_deleted` или `deleted_at`.

Логика такая:

- справочные / долгоживущие сущности, на которые уже могут ссылаться исторические факты, физически не удаляем;
- транзакционные таблицы вроде строк чека не обязаны иметь soft delete просто потому, что такое требование существует для справочников.

Варианты реализации soft delete:

- `is_deleted BOOLEAN`;
- `deleted_at TIMESTAMPTZ NULL`.

`deleted_at` обычно информативнее, потому что показывает не только факт удаления, но и момент.

### Особый случай CRM

Для клиента требование сильнее:

- физическое удаление запрещено;
- клиент должен исчезнуть из аналитического представления;
- контакты должны быть обезличены или обнулены;
- исторические продажи при этом сохраняются.

Это отдельное бизнес-правило, а не просто общий soft delete.

## 3. Surrogate PK и business key — не одно и то же

Запрещено использовать `serial` как business key, но внутренний числовой PK допустим.

Нормальная схема:

```text
id BIGINT PRIMARY KEY
sku_bk TEXT UNIQUE NOT NULL
```

Где:

- `id` — внутренний surrogate key для FK внутри одной БД;
- `sku_bk` — стабильный business key для интеграции, contract views и будущего DWH.

Главное требование: наружу идентичность сущности должна идти по business key, а не по внутреннему числовому id.
