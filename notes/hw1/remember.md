# HW1 — помнить

Краткий список ограничений и требований, которые важно держать перед глазами при проектировании четырёх исходных баз данных.

## Общие правила

- Четыре логических сервиса / четыре базы PostgreSQL: CRM, Catalog, POS, WMS.
- Для каждой сущности обязателен стабильный человекочитаемый business key.
- Суррогатные PK можно использовать внутри базы, но они не являются интеграционным идентификатором.
- Между разными сервисными базами нельзя делать FOREIGN KEY. Межсервисные ссылки — логические, по business key.
- В каждой таблице нужны технические поля, как минимум `created_at` и `updated_at`.
- `updated_at` должен обновляться автоматически средствами БД.
- Для изменяемых атрибутов нужно осознанно выбрать стратегию хранения истории.
- Если справочное значение может измениться после совершения факта, при необходимости нужно сохранять snapshot.
- Для справочников и сущностей, которые нельзя физически удалять, используем soft delete.
- Денежные значения — `numeric` фиксированной точности.
- Валюта — код ISO 4217.
- Представления в схеме `contract` — внешний интерфейс наших источников. Внутреннюю физическую модель мы выбираем сами.
- Контрактные VIEW должны быть детерминированными: не использовать `now()`, `current_date`, `random()` в их определениях.

## Инварианты, под которые нужно проектировать модель

### I1 — business key уникален
У каждой сущности BK должен быть уникальным.

### I2 — business key неизменяем
Попытка изменить существующий BK через `UPDATE` должна завершаться ошибкой.

### I3 — сумма чека равна сумме его позиций
Это правило между двумя таблицами. Проверка должна происходить в конце транзакции.
Ожидаемый механизм — deferred `CONSTRAINT TRIGGER`.

### I4 — арифметика строки чека
Одновременно должны выполняться условия:
- `quantity > 0`
- `unit_price >= 0`
- `line_discount >= 0`
- `line_discount <= quantity * unit_price`
- `line_amount = quantity * unit_price - line_discount`

### I5 — интервалы действия цены не пересекаются
Для одной комбинации `(sku, price_scope, scope_bk)` интервалы `[valid_from, valid_to)` не должны пересекаться.

Предполагаемый механизм:
- `btree_gist`
- `EXCLUDE USING gist`

### I6 — только одна текущая версия
Для одного ключа истории нельзя иметь две строки с `is_current = true`.

Естественный вариант реализации — partial unique index.

### I7 — остаток не может быть отрицательным
Никакая вставка, запись движения или списание не должны приводить к отрицательному остатку партии в конкретной локации.

### I8 — просроченную партию нельзя продать
POS должен отклонять строку чека, если дата чека позже `expiry_date` партии.

### I9 — просроченную партию нельзя принять на склад
WMS должен отклонять приёмку, если на момент приёмки срок годности партии уже истёк.

### I10 — рецептурный товар нельзя продать без рецепта
Если у строки чека `is_rx_snapshot = true`, у чека должен быть указан рецепт.

Важно: источник истины по признаку Rx живёт в Catalog, но POS должен уметь проверить это правило локально. Наше решение нужно будет отдельно зафиксировать в ADR.

### I11 — возврат не может превышать продажу
Суммарное возвращённое количество SKU по всем возвратам не должно превышать количество этого SKU в исходной продаже.

### I12 — сумма оплат равна сумме чека
Как и I3, это межтабличный инвариант, который логично проверять в конце транзакции через deferred constraint trigger.

## Положительные проверки

### P1 — `updated_at` обновляется автоматически
Если строку изменить без явного изменения `updated_at`, значение всё равно должно обновиться.

### P2 — soft delete клиента
После soft delete клиент должен:
1. исчезнуть из `contract.v_customer`;
2. физически остаться в таблице;
3. потерять или обезличить контактные данные.

## Правила тестов

- Один негативный SQL-файл на один инвариант.
- Тест должен быть самодостаточным.
- `COMMIT` и `ROLLBACK` внутри теста не пишем — транзакцией управляет чекер.
- Нельзя ослаблять схему внутри теста.
- Ожидаемый `SQLSTATE` нужно проверить экспериментально.
- Положительный тест должен вернуть одну строку с `ok = true`.

## Подготовка к CDC и следующим HW

- `wal_level = logical`.
- Publication должна покрывать нужные исходные таблицы.
- Нужно корректно выбрать `REPLICA IDENTITY`.
- Для инкрементальной выгрузки используем `updated_at`, где это подходит.
- Удаления / soft delete должны быть наблюдаемыми.
- Business keys нужно спроектировать сейчас так, чтобы в HW2 сущности можно было стабильно склеивать.

## Что легко забыть из контракта

- В строке чека POS нужно сохранять snapshot на момент продажи:
  - цену;
  - название SKU;
  - признак рецептурности.
- Продажа всегда ссылается на конкретную партию.
- Возврат всегда ссылается на исходную продажу.
- Один чек может оплачиваться несколькими способами.
- Цена может действовать на уровне:
  - всей сети;
  - региона;
  - конкретной аптеки.
  Более узкая область имеет приоритет.
- У одного SKU может быть несколько действующих веществ — связь M:N.
- У клиента за жизнь может быть несколько карт лояльности, но активная только одна.
- Согласия версионируются; активное согласие одного типа только одно.
- Номер серии партии уникален в рамках SKU.
